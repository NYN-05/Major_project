Implementation Work Division and Deliverables
Checklist

Project Context

This document divides the implementation work of the project DeepFake Video Detection
System for Video KYC in Financial Systems Using rPPG and Quantum Machine Learning on
Low-Resolution Videos among three team members: Aswin, Sumit, and Jhashank. The work
breakdown follows a deliverable-oriented machine learning pipeline, where large system
modules are split into smaller work packages so that multiple team members can work in
parallel instead of waiting for one linear sequence to finish [web:255][web:257][web:261].

The system itself follows a typical deepfake detection structure with input handling,
preprocessing, feature extraction, classification, and evaluation, which makes it practical to
assign ownership module by module [web:256][web:259]. Since the project is based on a two-
stage architecture where rPPG is the primary evidence layer and quantum machine learning is
the final decision layer, the task split below is organized around those technical blocks
[web:213][web:219].

The division is designed so that all three members contribute to implementation, but the
coding load is not identical because responsibilities are matched to skill profile and project
needs [web:255][web:261]. This also allows all three to work at the same time on different
deliverables under the same architecture [web:257][web:258].

Working Rule

Each architecture block below contains three things:

Owner: person mainly responsible.

Support: person who helps with checking, testing, or integration.

Deliverables checklist: concrete tasks that can be ticked.

A task is considered complete only when its code, output, folder structure, and validation
notes are all available in the shared project workspace [web:255][web:258].

Practical Note

This split is balanced because Sumit owns the full data and face pipeline, Jhashank owns the
full signal and model pipeline, and Aswin owns the full preprocessing policy, experiment
control, evaluation, and integration pipeline [web:255][web:261]. All three roles are
implementation roles, and all three can proceed in parallel as long as agreed input-output
formats are fixed at the start [web:258][web:259].
